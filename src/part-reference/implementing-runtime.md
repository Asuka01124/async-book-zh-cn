# 实现你自己的运行时

上游只有英文目录标题，没有英文正文；标题由 GPT-6 Luna 翻译，正文由 GPT-6.1 Sol 原创补写。理解运行时的好方法是实现一套小而完整的“任务—通知—等待”闭环。本章的 MiniRuntime 用安全 Rust 在当前线程驱动任务、处理计时器并执行取消/关闭；它是可运行的教学执行环境，没有实现生产网络 I/O、工作窃取或服务级公平性。

## 一次 wake 如何成为一次 poll

Future 不选择在哪个线程执行。执行器负责保存 Future，把可推进的任务排入就绪队列，给它对应的 Context，然后调用 poll。返回 Ready 时从任务表删除；Pending 时保留状态，等待 Waker 重新安排。驱动器则把时间或操作系统事件转换成 wake，二者职责不同。

我们的任务表保存 `Pin<Box<dyn Future<Output = ()>>>`，允许任务持有 Rc 等非 Send 状态；任务只在创建运行时的线程轮询。可跨线程的 Waker 不持有 Future，只持有任务 ID 和队列的 Weak 引用。外部线程因此只能发出通知，不能拿到或并发轮询任务本体。任务 ID 使用 checked_add，绝不回绕复用；迟到事件不会命中新任务。

[`std::task::Wake`](https://doc.rust-lang.org/std/task/trait.Wake.html) 可从 Arc 构造 Waker，比自己维护 RawWakerVTable 的引用计数与unsafe边界更适合入门。下面是完整的调度部分；定时器字段和方法定义紧随其后，来自同一个已编译源码文件：

spawn 把任务首次入队。tick 从队列取出一个 ID，放开队列锁，再查任务表并 poll。Waker 在 poll 内被调用也能立即入队，因为 poll 期间没有持有队列锁；当前 Pending 返回后，下一次 tick 就能看见该通知。若 Ready 与通知交错，后续只会遇到已经删除的 ID，并安全跳过。

这个设计允许重复通知形成重复队列项，正确性依赖重新检查任务是否存在，不依赖“每个 wake 恰好对应一个 poll”。它的队列可能膨胀，生产执行器一般增加 queued/running/completed 等原子状态并合并通知。合并时又必须正确处理“正在 poll 时收到 wake”，不能因为任务正在执行就丢掉这个通知。

## 空闲时等待，不能扫描式空转

一个反复遍历所有任务并 poll 的无限循环，可能碰巧跑完简单示例，却把 CPU 全用来查询还没有变化的状态。也不能在看到队列空后直接睡眠：若此时外部事件刚入队，通知可能早于睡眠而丢失。

本实现用 [`Condvar`](https://doc.rust-lang.org/std/sync/struct.Condvar.html) 与队列共享的 Mutex 保持谓词：只有在持锁观察到 ready 为空时才 wait，wait 原子地释放锁并进入等待。生产者必须取得同一把锁才能入队与通知，所以“检查为空—释放锁等待”之间没有不受保护的空隙。条件变量允许虚假唤醒，while 循环重新检查队列。

也可以用 [`thread::park/unpark`](https://doc.rust-lang.org/std/thread/fn.park.html)，但它们是线程级令牌，嵌套执行或未知代码中的 park 可能消费别人的令牌。官方 Wake 示例也明确指出简单 park 版本的嵌套调用边界。教学代码改用自己拥有的条件变量，不声称任意 block_on 都可以在任意执行器中嵌套。

run 一直驱动到任务表为空；若某个 Pending 任务既没有定时器也永远没有外部事件，它会等待下去，这是任务缺少完成条件，不应靠定期强制 poll 掩盖。调用者要在生命周期设计中提供正常完成或取消路径。

Sleep 首次 poll 在未到期时注册通知，后续 poll 在 fired 状态返回成功。检查状态与替换 waker 在同一把锁内完成；clone 在锁外，旧句柄在释放锁之后销毁，以免自定义回调重入。定时器先到期也没有问题：第一次 poll 会直接观察 fired，不需要历史通知仍在。

Sleep 被丢弃时清理注册，驱动器只持有 Weak，因此下次扫描可以移除过期登记，不让取消的定时器保活整个任务。shutdown 会把还登记的计时器标记 closed，并通知仍保存在运行时之外的 Sleep，以 Err(TimerClosed) 结束；已到期并移出登记的 Sleep 已经完成，不再追溯改为关闭错误。本例明确允许完成后的 Sleep 再次读取同一状态，但这只是此实现的保证，不能推广到一般 Future。

计时器列表用线性扫描和 min，是教学取舍；高负载运行时常用堆、时间轮或更紧凑的登记表，并处理删除、ID复用、精度与溢出。这里 checked_add 拒绝无法表示的期限，不提供实时调度承诺。到期仅使任务可运行，长时间 poll 仍会延迟它。公开 tick 只处理一次就绪队列，不独立驱动计时；完整的驱动入口是 run。

示例不承诺极短计时器的完成先后：操作系统调度或进入 run 之前的延迟可能使多个期限都已经到达。业务顺序应编码在依赖或序号中；测试比较得到的值，避免把毫秒时序偶然性当成保证。

MiniRuntime 的取消是宿主线程调用 `cancel(id)`，从任务表移除并同步销毁 Future。它不抢占正在执行的 poll；由于 run 借用 `&mut self`，本例也不提供另一个线程直接取消运行中任务的接口。若要让远程控制端取消，应增加发送控制消息的句柄，由运行线程在安全点处理，而不是给任务表加锁后从任何线程销毁非 Send 状态。

shutdown 的顺序是：关闭队列入口并清空就绪项，向未完成计时器发布关闭，最后销毁任务。此后不再允许 spawn 或 sleep。Wake 中的 Weak 队列引用不会保活已经销毁的运行时；队列尚存在但 closed 时，迟到通知被忽略。对本实现，关闭就意味着同步取消，并没有承诺异步业务清理已完成。

真正服务的优雅关闭还需要上层协议：停止接入，广播停止请求，等待任务确认，排空必要输出，再关闭驱动器。若先关闭驱动器，任务可能永远等不到清理所需的 I/O。超时后的强制取消只能销毁任务状态，不会逆转已发生的副作用。

run 仅在任务存在期间驱动，单独保存在外部而没有被任务等待的 Sleep 不会让 run 长驻；运行时本身也必须活到资源使用结束。宿主必须明确决定哪一个 Future 或任务集合代表服务的生命期。

## 距离网络运行时还有什么

生产 I/O 驱动器需要登记 socket/handle、关注读写方向、保存对应 Waker，并把 [`mio::Poll`](https://docs.rs/mio/latest/mio/struct.Poll.html) 等接口报告的事件映射回资源。就绪只说明可以尝试操作，仍须处理 WouldBlock 和虚假事件；资源关闭、句柄复用和陈旧事件要求代际 ID 或等效保护。完成式 I/O 还须在 Future 被丢弃后保留内核可能访问的缓冲区，不能只删除任务表项。

驱动器等待和队列等待也要整合：不能让线程无限阻塞在网络 poll 中而忽略新 spawn 或更早的计时器。常用额外唤醒句柄或把控制事件登记到同一事件循环。多个工作线程还需要防止同一 Future 被同时 poll，并处理通知合并、窃取、队列公平性、线程退出与panic传播。

本实现没有处理任务 panic 的隔离，panic 会向宿主传播，运行时析构执行取消；锁中毒采用 unwrap，不承诺故障恢复。没有共享 spawn 句柄、任务结果 JoinHandle、结构化子任务、并发队列容量限制、CPU预算或网络能力。不宜把这份示例复制进生产服务后宣称完成了通用运行时。

本章四测试验证真实定时器/非 Send 任务、poll 内 wake 不丢失、已 Pending 后由外部线程唤醒且总共只有两次 poll、取消/陈旧通知/外部计时器关闭。它们实际运行了教学调度器与时间驱动器；没有运行内核网络 I/O 驱动或多线程工作窃取模型。
