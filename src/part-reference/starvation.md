# 饥饿

上游只有英文目录标题，没有英文正文；标题由 GPT-6 Luna 翻译，正文由 GPT-6.1 Sol 原创补写。

饥饿是指某项工作长时间没有取得应有进展，即使系统的其他部分仍在工作。异步程序的常见表现是吞吐量看似正常，关闭通知、心跳或某个连接的响应却一直得不到处理。死锁通常是依赖环让有关工作都无法推进；饥饿可能只影响一部分任务，原因也不一定在执行器。

## await 不等于调度点

Tokio 任务采用合作式调度：一次 poll 运行期间，执行器不能在任意指令处抢占这个 Future。调用同步阻塞 API 或持续进行 CPU 计算，会占住执行它的 worker。current_thread runtime 尤其明显；多线程能让其他 worker 推进工作，但足够多的阻塞任务仍能耗尽所有 worker。[任务文档](https://docs.rs/tokio/latest/tokio/task/index.html) 解释了这个基本模型。

即使循环里有 await，也不一定交还控制权。如果子 Future 不断 Ready，await 会在同一个外层 poll 中继续执行后续代码。例如从始终就绪的 Stream 连续取值、不断 await ready(()), 或不断重试一个立即返回错误的函数，都可能让单次 poll 变得无限长。停止令牌、定时器和其他 select 分支没有执行机会时，也就不能及时终止它。

Tokio 的一些 I/O、通道等原语参加合作式预算，在消耗预算后暂时 Pending，让外层任务有机会返回执行器；[coop 文档](https://docs.rs/tokio/latest/tokio/task/coop/index.html) 说明了这种机制。它不是 Rust 语言的自动抢占：纯计算、第三方 Future、自定义 Stream，以及 unconstrained 包装都未必受它约束。不要把某个版本的预算数值当作程序正确性依赖。

项数上限只有在每项耗时有上限时，才间接限制 poll 时长。一次“处理一帧”如果能解析无限大的输入，预算为一仍可能很慢。需要同时限制输入大小、单步计算复杂度与批量大小。这个例子还一次性拥有整个 Vec，既没有限制输入总内存，也没有将计算分配到多个 CPU 核。

对较长的纯计算，使用有限的 CPU 工作池通常比在异步 worker 上频繁切片更合适；有界阻塞调用可以交给 spawn_blocking，但也应限制并发。工作池隔离不会使计算自动可取消，过多后台任务仍可能耗尽内存和 CPU；见 [同步与异步桥接](sync-async.md)。

## yield_now 提供机会，不承诺顺序

在应用循环中，处理一小批工作后 await tokio::task::yield_now() 是常见的合作方法。它让当前任务重新进入就绪队列，减少一次 poll 长期占用线程的机会。但 [yield_now 的非保证](https://docs.rs/tokio/latest/tokio/task/fn.yield_now.html#non-guarantees) 明确指出：运行时可能马上再次轮询同一任务；组合器也可能吞掉这次让出，例如 select 中另一个分支在同一次 poll 完成。

因此不能用 yield_now 表达“某个别的任务一定已经执行”、固定轮转顺序或时间期限。需要先后关系时，用通道、通知、Barrier 或显式确认。需要减少空轮询时，应等待真实事件；在 try_recv 返回 Empty 后 yield 再重试，仍比直接 recv().await 浪费调度。

Tokio 的 [运行时公平性保证](https://docs.rs/tokio/latest/tokio/runtime/index.html#detailed-runtime-behavior) 带有前提：任务总数有界，且每次 poll 的持续时间有界等。在这些假设下，被唤醒任务会在某个有限延迟内被调度；它不承诺相等的时间片或固定顺序，更不是实时截止时间保证。无限创建任务或无限 poll 都破坏这些前提。

## select 内部也会饥饿

执行器公平地轮询某个任务，不代表任务里的分支都公平。tokio::select 默认随机选择首先检查的分支，为循环提供一定公平性；这不等于每个分支在指定次数内必定获选。如果使用 biased，分支按书写顺序检查，用户需要自己负责顺序。[select 公平性文档](https://docs.rs/tokio/latest/tokio/macro.select.html#fairness) 特别提示了高流量输入和关闭信号的关系。

把永远就绪的数据分支放最前面，会让后面的停止分支甚至没有被 poll。将一次性关闭分支放前面并在触发后退出，常常合理；有多个持续就绪的数据源时，则要轮转优先级、按源限制一轮处理量，或者用明确的队列调度规则。select 的 else 只在所有分支被禁用时执行，不能当成“当前其他分支均 Pending 的空闲分支”。

注意，这里的公平与取消安全是两件事。通过轮转让分支有机会执行，仍要检查每次竞争失败时是否会销毁半帧进度；见 [取消与取消安全](cancellation.md)。

## 锁与资源分配也可能让请求饿死

繁忙任务反复 try_lock/try_acquire，失败就立即重试，会把本可用于持有者释放资源的执行机会消耗掉。应等待锁或许可，缩短持有时间，避免在 guard 还活着时等待依赖同一资源的其他任务。普通 Mutex 的公平策略取决于具体实现，不能从“互斥”一词推导 FIFO。

Tokio Mutex 的 lock 使用 FIFO 等待顺序，但取消等待会失去排队位置。如果调用者不断把 lock 与短定时器竞争并重建，即使锁本身按队列服务，也可能让自己一直排到后面。Semaphore 的公平队列还意味着队首的大额 acquire_many 可能阻挡后面的小额申请。这是有意的公平策略与吞吐量权衡，不意味着任务调度器坏了。官方约束见 [Mutex](https://docs.rs/tokio/latest/tokio/sync/struct.Mutex.html) 与 [Semaphore](https://docs.rs/tokio/latest/tokio/sync/struct.Semaphore.html)。

资源优先级也可能间接反转：高优先级请求等待低优先级任务持有的连接，后者又被繁忙数据循环延迟。为重要控制通路预留容量、减少锁内工作、避免持锁调用外部代码，并把真实任务/资源依赖画清楚，比简单增加 worker 数量更可靠。

## 用背压减少竞争，用观测定位问题

过载时无限增长的队列会延长等待，掩盖“任务都在执行但请求永远排不到”的问题。应该限制入口、在途并发、字节预算与重试量，在容量耗尽时拒绝、合并或上游等待。有界队列本身也不保证每个租户公平；可按连接、用户或优先级分队列，再对各队列设置配额。

观测时同时记录排队时间、单次处理耗时、任务数、队列长度、锁等待与截止时间错过，而不只看平均吞吐量。延迟尖峰可能来自同步阻塞、巨大 poll、优先分支或资源排队；CPU profiler 与任务追踪应结合这些业务指标解释。不要先通过提高全局超时掩盖停止分支根本没有运行的问题。

## 本章验证边界

三个有界测试验证：七次立即 Ready 的 await 会在一次外层 poll 全部完成；BudgetedSum 每次最多推进两项、未完成时确实自唤醒，并允许调用者在两次 poll 之间轮询另一项工作；五轮 biased select 中始终 Ready 的前分支使后分支一次也未被 poll，并验证有限停止分支放前的选择。

这些是确定性的行为模型，不会真的执行无限循环，不依赖毫秒级墙钟断言。手动穿插另一个 Future 证明调用者已经拿回控制权，并不证明真实运行时必定按这个顺序调度；本章没有把测试称作生产调度公平性或实时延迟的证明。没有新增依赖或性能基准。
