# 设计模式

上游只有英文目录标题，没有英文正文；标题由 GPT-6 Luna 翻译，正文由 GPT-6.1 Sol 原创补写。

异步设计首先要回答三个问题：谁拥有可变状态，哪里限制正在等待和执行的工作，谁负责确认所有工作已经结束。选择组合器只是实现这些决策的最后一步。下面以连接服务、批量处理和后台任务为场景说明常用模式。

## 单一所有者与请求/响应

数据库连接、协议编码器和写入器往往有内部状态，调用还需要 await。与其让许多调用者持有异步锁，可以让一个任务拥有资源，其他任务通过有界 mpsc 发送命令，每条命令带一个 oneshot 响应端。这就是常说的 actor 或资源管理任务。[Tokio 通道教程](https://tokio.rs/tokio/tutorial/channels) 展示了这种安排。

这样可以明确串行化请求的范围、统一重连和关闭，并将资源借用限制在所有者内部。它不会凭空提高吞吐量：所有者如果收到一条请求就一直 await 到结束，其他请求仍会等待。协议允许流水化时，可以在所有者内部维护请求 ID 与在途响应表；不能为了并发而打乱协议规定的顺序。

## 有界入口让背压贯穿系统

容量为 N 的队列只限制队列中消息的数量，不限制消息的字节大小、生产者创建消息占用的内存，或已经取出的在途工作。应根据负载同时设置请求大小、队列容量、执行并发和上游接纳策略。例如上传服务可以先拿字节预算再读取请求体；若先读完整个文件再等队列，队列有界也挡不住大量生产者占满内存。

满队列时有几种不同的业务选择：await send 让上游等待；try_send 返回忙碌并拒绝；合并同一键的待更新值；或写入有容量和恢复协议的持久队列。不能把 send 包进无限 spawn 来“解除阻塞”，那只是把等待从队列搬到了未受限的任务中。等待队列也可能需要超时、最大等待者数量或连接接入限额。

若 select 中取消 send，已经移进发送 Future 的命令可能被销毁。需要在放弃等待时仍持有命令，可先 await [reserve](https://docs.rs/tokio/latest/tokio/sync/mpsc/struct.Sender.html#method.reserve) 取得容量，然后同步提交值；等待许可的取消会失去排队位置。许可本身也属于生命周期：不要长期囤积许可，否则队列即使看似空着也可能无法接收。

## 关闭是一个协议

示例把关闭请求与命令通道分开，避免满队列阻止关闭指令进入。收到关闭后，Receiver::close 拒绝新的普通发送，接着继续 recv 排空已接受消息；直到 None 才返回最终状态。因此外部仍持有 Sender 时，也能完成关闭。关闭通知的发送端意外丢弃同样触发关闭，这是本例明确选定的宿主失联策略。

这里使用 biased 是因为关闭分支只需执行一次，而且会由 closing 禁用；它不应该被照搬到永远就绪的数据分支之前。有界的普通请求仍会排空。若扩展 API 允许调用者持有发送许可，close 之前取得的许可仍能发送，必须等这些许可释放或使用后才能读到最终 None；本例未在测试里引入预留许可。[mpsc 的关闭说明](https://docs.rs/tokio/latest/tokio/sync/mpsc/index.html#clean-shutdown) 给出了相应协议。

真实写入器通常还要在排空后 await flush/close，然后宿主 await 所有者的 JoinHandle。发送停止通知与确认退出是两步；直接丢弃 JoinHandle 会分离 Tokio 任务。若任务因为 I/O 错误或 panic 提前退出，等待中的响应端会断开，宿主也必须检查任务结果并决定拒绝后续请求、重建连接还是退出进程。

正常排空可能没有时间上限。若业务要求在期限内退出，应明确期限耗尽后会丢弃哪些请求、如何向等待者报告，以及副作用是否可能已经提交。abort 只能作为已定义的升级策略，不能替代必要的异步资源清理。一般关闭流程是停止接纳、通知已有工作、等待完成；见 [Tokio 关闭指南](https://tokio.rs/tokio/topics/shutdown)。

## 批量任务：限制并发，再决定结果顺序

抓取一批 URL 或处理对象列表时，如果无需让任务独立存活，优先在当前 Future 内组合工作。将输入映射为 Future，用 buffer_unordered(limit) 只同时推进有限个操作；需要输入顺序时使用 buffered(limit)，但前面的慢请求会延迟后面已完成结果的交付。两者及其代价见 [Stream 一章](../part-guide/streams.md) 和 [StreamExt 文档](https://docs.rs/futures/latest/futures/stream/trait.StreamExt.html#method.buffer_unordered)。

并发限制与速率限制不同：最多十个在途请求，仍可能在一秒内完成数千次。外部服务的每秒速率需要额外的令牌或时间窗口。重试同样消耗预算，并应有最大次数、总期限和退避；不要在共享锁内睡眠，也不要在不确定请求是否提交时盲目重试。

当子工作必须单独 spawn 时，宿主可以用 [JoinSet](https://docs.rs/tokio/latest/tokio/task/struct.JoinSet.html) 收集完成结果，同时限制 set 的长度，在有空位时才生成下一项。每个结果要分别处理 JoinError 与业务 Result；一项失败后，是继续、停止接纳并等现有工作，还是取消其他工作，应由业务决定。JoinSet 的 Drop 会请求中止其中任务；需要确认析构或汇总错误时，显式中止后继续 join。它不会将已开始的 spawn_blocking 工作变成可强制取消的计算。

## 多阶段管线与资源池

读取、解析、写入可以组成管线，各阶段之间放有界队列：慢写入器让解析器停止发送，再逐渐让读取器停止接纳。并发阶段会改变完成顺序，若输出要求顺序，需加入序号和有界重排窗口。不能无限保存“后来的结果”等待第一项，否则又失去内存界限。

一个阶段退出时，应由监督者关闭相关入口、通知其他阶段并等待它们退出。下游提前失败后，上游发送失败应终止或转入错误处理，不能 unwrap 后只留下一个 panic；上游错误也应作为消息或独立结果传给下游，不能让“流结束”悄悄代表成功。各阶段若同时等待对方清空队列，必须检查关闭顺序是否构成循环依赖。

连接池则把有限数量的资源借给请求，而不是把所有操作串在一个所有者任务里。池许可应跟随真实资源使用期，尤其是阻塞工作或后台操作，不能因为外层 Future 取消就提前归还。许可计数只控制并发，不负责连接健康检查、事务回滚和故障连接隔离；这些由池的安全包装和资源协议承担。有关阻塞工作许可的实测例子见 [同步与异步桥接](sync-async.md)。

## 简单状态不必都变成 actor

对于短小、不跨 await 的内存更新，普通 Mutex 常常更直接：在小作用域内复制或更新状态，释放 guard 后再 await。异步 Mutex 适合确实要跨 await 独占访问的场景，但长时间持锁可能让所有请求串行，并增加锁顺序和关闭依赖。应衡量操作边界与争用，而不是只看调用者是否 async；[Tokio 共享状态教程](https://tokio.rs/tokio/tutorial/shared-state) 对这两种策略作了区分。

通知也要匹配业务语义。每条事件都不能丢，使用有背压的事件队列；只关心当前配置，watch 保存最新状态更合适；一次请求对应一次答复，使用 oneshot。watch 会合并中间更新，不适合审计记录；借用 watch 值的 guard 应在 await 前释放。[watch 文档](https://docs.rs/tokio/latest/tokio/sync/watch/index.html) 说明了版本观察与关闭规则。

## 本章验证边界

共享源码的三个测试分别验证：满队列发送确实先返回 Pending，关闭后拒绝这次发送并排空原消息，即使 Sender 仍活着；调用者放弃响应后状态变化仍保留；业务溢出不污染状态且服务继续响应。它们使用真实 Tokio 通道和任务，没有依赖墙钟延时。

计数器只模拟状态所有权，未连接真实数据库、没有持久性、网络重连或性能测试。管线、连接池和重试策略是设计讨论，没有把它们记作已实现的集成测试。本章核查的 Tokio 文档版本为 1.54.1，API 与具体运行时选择仍应以项目锁定版本为准。
