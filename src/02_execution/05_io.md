# 执行器与系统 IO {#executors-and-system-io}

在上一节[《`Future` trait》]中，我们讨论过下面这个在套接字上执行异步读取的 Future 示例：

```rust,ignore
{{#include ../../examples/02_02_future_trait/src/lib.rs:socket_read}}
```

这个 Future 的设计意图是读取套接字上已就绪的数据（所引 `Socket` 实际仍是前文明确标注的教学占位，并未执行网络 I/O）；如果没有数据可读，它就会让出执行权，并请求执行器在套接字再次变为可读时唤醒对应任务。不过，从这个示例中看不出 `Socket` 类型是如何实现的，尤其是 `set_readable_callback` 函数究竟如何工作并不明显。我们怎样才能安排在套接字变为可读时调用 `wake()`？一种做法是启动一个线程，不断检查 `socket` 是否可读，并在适当的时候调用 `wake()`。但这种方式效率很低，若为每个等待中的 IO Future 都单独这样做，就需要占用大量线程，这会大幅降低异步代码的效率。

实际中，可以集成能同时等待多个 IO 事件的系统机制，例如 Linux 的 `epoll`、FreeBSD 和 macOS 的 `kqueue`，以及 Windows 的 IOCP。这里必须区分两类通知：就绪模型提示某类操作可能不会阻塞，程序仍需实际读写；完成模型通知已提交操作的完成结果。[Windows IOCP](https://learn.microsoft.com/en-us/windows/win32/fileio/i-o-completion-ports) 主要采用完成模型，不能把所有通知都解释成“可读”，也不能把可读通知当作读取已完成。

跨平台 Rust crate [`mio`] 提供统一的就绪接口，其 [Poll 文档](https://docs.rs/mio/1.2.4/mio/struct.Poll.html#implementation-notes) 说明 Windows 后端通过 IOCP 适配这套接口。上游旧文还列出了 Fuchsia 的 `port`；Fuchsia 确实有[等待 port 数据包的系统接口](https://fuchsia.googlesource.com/fuchsia/+/cc19d17b05c18cbc940da8ef6fa5bcc0d6464c1f/docs/reference/syscalls/port_wait.md)，但本次核查的 Mio 1.2.4 官方支持列表没有 Fuchsia，不能沿用“这些平台都由当前 Mio 支持”的旧断言。

下面保留一个概念性的等待接口，用于说明兴趣注册、事件 ID 和事件分发。它不是任何系统 API 或 Mio 的直接绑定，也不是可编译实现；真实 API 还会处理错误、超时、中断和成批事件：

```rust,ignore
struct IoBlocker {
    /* ... */
}

struct Event {
    // 应用为事件源登记的标识，用于将通知路由回注册项。
    id: usize,

    // 需要等待的一组信号，或已经发生的一组信号。
    signals: Signals,
}

impl IoBlocker {
    /// 创建一个新的异步 IO 事件集合，以便等待其中的事件。
    fn new() -> Self { /* ... */ }

    /// 表明要关注某个特定的 IO 事件。
    fn add_io_event_interest(
        &self,

        /// 事件将发生于其上的对象
        io_object: &IoObject,

        /// `io_object` 上可能出现、且会触发事件的一组信号，
        /// 并附带一个 ID，供由此关注项产生的事件使用。
        event: Event,
    ) { /* ... */ }

    /// 阻塞，直到其中一个事件发生。
    fn block(&self) -> Event { /* ... */ }
}

let mut io_blocker = IoBlocker::new();
io_blocker.add_io_event_interest(
    &socket_1,
    Event { id: 1, signals: READABLE },
);
io_blocker.add_io_event_interest(
    &socket_2,
    Event { id: 2, signals: READABLE | WRITABLE },
);
let event = io_blocker.block();

// 例如，如果套接字 1 变为可读，就打印 "Socket 1 is now READABLE"。
println!("Socket {:?} is now {:?}", event.id, event.signals);
```

运行时的 IO 驱动（也常称 reactor）可以利用这些原语提供异步 IO 对象（例如套接字），并配置在特定 IO 事件发生时运行的回调。对于上面的 `SocketRead` 示例，`Socket::set_readable_callback` 函数的概念性接线可以写成下面的伪代码。它与前文简化的 `fn()` 参数版本属于不同抽象层，不能直接粘贴拼接：

```rust,ignore
impl Socket {
    fn set_readable_callback(&self, waker: Waker) {
        // `local_executor` 在此示意当前运行时的 IO 驱动/注册设施。
        // 可以在创建套接字时提供它；但实际中，为了方便，
        // 部分运行时通过线程本地上下文传递它；也可以显式传参。
        let local_executor = self.local_executor;

        // 此 IO 对象的唯一 ID。
        let id = self.id;

        // 保存当前任务的 Waker，供事件分发使用；此处省略同步与防丢通知协议。
        local_executor.event_map.insert(id, waker);
        local_executor.add_io_event_interest(
            &self.socket_file_descriptor,
            Event { id, signals: READABLE },
        );
    }
}
```

上面仅展示映射关系。真实实现必须协调 IO 就绪状态、Waker 注册与消费：例如登记最新 Waker 后重新尝试非阻塞操作或检查受同步保护的就绪状态；事件路径先发布状态再取出句柄，并在锁外唤醒，替换旧句柄时也避免锁内自定义 clone/drop 回调。只做一次 `event_map.insert`，再期待未来出现新事件，可能错过已经发生的通知。一个对象上的多个等待者、读写分别等待、注销和 ID 复用也需要明确协议，不能用同一个 map 项无条件覆盖所有等待者。

Mio 的[可移植性约定](https://docs.rs/mio/1.2.4/mio/struct.Poll.html#portability) 特别要求处理伪就绪：收到通知仍可能读写出 `WouldBlock`，它表示应继续等待，而不是成功或致命错误。底层就绪消费者需要反复执行非阻塞操作直到 `WouldBlock`（或遇到 EOF/实际错误），否则不能保证后续一定还有通知。若上层只返回一次读取结果，驱动层必须保留尚未耗尽的就绪状态，或安排后续主动处理，不能把剩余进展遗失；若为公平性提前让出，也须确保再次被调度。不能为了“读完”改用阻塞 IO。关闭和错误最终以实际操作结果为准。

这样，一个 IO 驱动线程就可以等待许多事件，把通知分发给相关任务的 `Waker`，执行线程再轮询任务；驱动和执行也可以合并在一个线程中。这是实现选择，不要求运行时永远只有一个线程。已有可运行任务时应继续推进，并协调跨线程任务通知和下一次阻塞等待，避免执行器在仍有工作时睡眠。

本节没有实现真实 `IoBlocker`、系统驱动或完成式缓冲区生命周期管理，没有把伪代码当作 Linux、Windows 或 Fuchsia 的实测。就绪/完成、取消与缓冲区所有权的完整讨论见[异步 I/O 模型](../part-reference/io-models.md)，一般阻塞桥接见[IO 与阻塞问题](../part-guide/io.md)。
